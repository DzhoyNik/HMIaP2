# Лабораторная работа №1 — Система контроля доступа к ресурсам

Консольное приложение на Kotlin для управления доступом к иерархическим ресурсам с аутентификацией по логину/паролю и разграничением прав (чтение / запись / выполнение).

## Архитектура

Приложение построено по слоям, каждый из которых решает одну задачу и не зависит от деталей реализации соседних:

```
┌─────────────────────────────────────────────────────────┐
│                         Main.kt                          │
│        (точка входа, оркестрация, возврат exitCode)       │
└───────────────┬─────────────────────────────┬───────────┘
                │                             │
                ▼                             ▼
     ┌────────────────────┐        ┌───────────────────────┐
     │   CliParser         │        │   HelpPrinter          │
     │  (kotlinx-cli)      │        │  (текст справки)       │
     └──────────┬──────────┘        └───────────────────────┘
                │ распарсенные аргументы (login, password,
                │ path, action, volume)
                ▼
     ┌────────────────────┐
     │  AuthService        │──── PasswordHasher (SHA-256 + соль)
     │  (проверка логина/  │
     │   пароля)           │
     └──────────┬──────────┘
                ▼
     ┌────────────────────┐
     │  ResourceRepository  │──── ResourceNode (дерево ресурсов)
     │  (поиск ресурса по   │
     │   пути A.B.C)        │
     └──────────┬──────────┘
                ▼
     ┌────────────────────┐
     │  AccessController    │──── PermissionTable (права по
     │  (проверка прав с     │     пользователю и ресурсу)
     │   наследованием от     │
     │   родителя)            │
     └──────────┬──────────┘
                ▼
     ┌────────────────────┐
     │  VolumeValidator      │
     │  (проверка объёма      │
     │   относительно maxSize)│
     └──────────┬──────────┘
                ▼
        ResultCode (0..8)
```

### Компоненты

| Модуль | Ответственность |
|---|---|
| `CliParser` | Разбор аргументов через `kotlinx-cli`, валидация формата (флаги, обязательность полей) |
| `HelpPrinter` | Формирование и вывод текста справки по `-h` / `--help` |
| `PasswordHasher` | Генерация соли, хэширование пароля через `MessageDigest` (SHA-256), сравнение хэшей |
| `AuthService` | Проверка существования логина и корректности пароля пользователя |
| `ResourceNode` / `ResourceTree` | Иерархическая модель ресурсов (жёстко заданная в коде), поиск узла по пути вида `A.B.C` |
| `PermissionTable` | Хранение прав `(login, resourcePath) -> Set<Action>`, жёстко заданное в коде |
| `AccessController` | Проверка прав с учётом наследования от родительских ресурсов |
| `VolumeValidator` | Сравнение запрошенного объёма с максимально допустимым для ресурса |
| `ResultCode` | Enum с кодами 0–8 и их маппингом на exit code процесса |
| `Main` | Связывает все компоненты по порядку проверок и возвращает `exitProcess(code)` |

### Порядок проверок (важно для корректных кодов ответа)

1. Если передан `-h`/`--help` или аргументы некорректны по формату → справка, код **1**.
2. Валидация формата ресурса/пути и объёма (регулярка на имя, парсинг числа) → код **7**, если некорректны.
3. Проверка существования логина → код **3**, если логина нет.
4. Проверка пароля (хэш + соль) → код **2**, если неверен.
5. Проверка существования ресурса по пути → код **6**, если не найден.
6. Проверка, что действие входит в `{read, write, execute}` → код **4**, если неизвестно.
7. Проверка прав доступа (с наследованием от родителя) → код **5**, если доступа нет.
8. Проверка объёма относительно максимума ресурса → код **8**, если превышен.
9. Иначе — код **0**.

> Порядок проверок стоит зафиксировать в коде явно (например, отдельной функцией `validate(): ResultCode`), чтобы тесты `test.sh` предсказуемо получали нужный код на каждый кейс.

## Декомпозиция задач

Работа делится на две части так, чтобы участники могли работать параллельно и пересекались только на этапе `Main.kt` и `ResultCode`.

### Участник 1 — CLI, аутентификация, сборка

- [ ] Настроить структуру проекта без систем сборки, подключить `kotlinx-cli` как jar в `lib/`
- [ ] Реализовать `CliParser` (флаги `--login`, `--password`, `--resource`, `--action`, `--volume`, `-h/--help`)
- [ ] Реализовать `HelpPrinter` с описанием всех флагов
- [ ] Реализовать `PasswordHasher` (генерация соли, `MessageDigest` SHA-256, сравнение)
- [ ] Реализовать `AuthService` с захардкоженной базой пользователей (логин, соль, хэш пароля)
- [ ] Написать `build.sh` и `run.sh`
- [ ] Написать `test.sh` (совместно с участником 2, каждый готовит кейсы под свою часть)

### Участник 2 — Ресурсы, права, объём

- [ ] Реализовать `ResourceNode`/`ResourceTree`: захардкоженное дерево ресурсов, парсинг пути `A.B.C`, валидация имени по regex (≤20 символов, [A-Za-z0-9_])
- [ ] Реализовать `PermissionTable`: захардкоженные права по каждому пользователю и ресурсу
- [ ] Реализовать `AccessController` с логикой наследования прав от родителя к потомку
- [ ] Реализовать `VolumeValidator` (парсинг целого числа, сравнение с maxSize ресурса)
- [ ] Реализовать `ResultCode` (enum + маппинг на exit-код процесса)
- [ ] Собрать `Main.kt`: последовательный вызов всех проверок в правильном порядке
- [ ] Составить `readme.md` (этот файл) и финально сверить с реализацией

### Общее

- Оба участника договариваются заранее о:
    - формате хранения пользователей/ресурсов/прав в коде (например, `data class` + `val` таблицы);
    - точных сигнатурах между модулями (что возвращает `ResourceTree.findByPath()`, что принимает `AccessController.check()`), чтобы не блокировать друг друга;
    - наборе тестовых данных (логины, пароли, ресурсы, права), которые будут «зашиты» в программу и использованы в `test.sh`.

## Коды ответа

| Код | Описание |
|---|---|
| 0 | Успешное выполнение |
| 1 | Запрошена справка |
| 2 | Неверный пароль |
| 3 | Неверный логин |
| 4 | Неизвестное действие над ресурсом |
| 5 | Нет доступа |
| 6 | Несуществующий ресурс |
| 7 | Некорректный формат ресурса или объёма |
| 8 | Превышение максимального объёма |

## Сборка и запуск

Системы сборки (Gradle/Maven) не используются — компиляция производится напрямую через `kotlinc`.

```bash
# Сборка
./build.sh

# Запуск
./run.sh --login alice --password qwerty --action read --resource A.B.C --volume 10
```

Пример содержимого `build.sh`:

```bash
#!/bin/bash
kotlinc -cp "lib/kotlinx-cli-jvm.jar" src/main/kotlin/**/*.kt src/main/kotlin/Main.kt \
  -include-runtime -d app.jar
```

Пример содержимого `run.sh`:

```bash
#!/bin/bash
java -jar app.jar "$@"
```

> Запуск `.sh`-файлов возможен из Git Bash или WSL на Windows.

## Тестирование

`test.sh` прогоняет программу с фиксированным набором аргументов — по одному кейсу на каждый из 9 кодов ответа (0–8) — и сверяет фактический exit code с ожидаемым.

Формат вывода:

```
Test 0 (success): OK
Test 1 (help): OK
Test 2 (wrong password): OK
Test 3 (wrong login): OK
Test 4 (unknown action): OK
Test 5 (no access): OK
Test 6 (resource not found): OK
Test 7 (invalid format): OK
Test 8 (volume exceeded): OK
------------------------
Итого: 9/9
```

Запуск:

```bash
./test.sh
```

## Формат аргументов

```bash
$ java -jar app.jar --login alice --password qwerty --action read --resource A.B.C --volume 10
```

| Флаг | Обязательный | Описание |
|---|---|---|
| `--login` | да | Логин пользователя |
| `--password` | да | Пароль пользователя (в открытом виде, хэшируется внутри программы) |
| `--resource` | да | Путь до ресурса вида `A.B.C` |
| `--action` | да | Действие: `read`, `write` или `execute` |
| `--volume` | да | Запрашиваемый объём ресурса (целое число) |
| `-h`, `--help` | нет | Вывод справки |
